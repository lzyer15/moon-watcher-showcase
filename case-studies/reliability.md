# 사례 2 · 프로세스 실행과 실제 감시 진행을 구분하기

## 문제

서비스 프로세스는 실행 중인데 감시 heartbeat가 멈춘 적이 있었다. VM 한 대에서 운영하다 보니 서버 상태를 더 자세히 확인해야 했다. 이후에는 메모리 부족으로 감시 프로세스가 강제 종료된 사실도 커널 기록에서 확인했다.

화면 조회용 스트림 프로세스가 여러 개 남아 있는 것도 확인했다. 다만 이 현상만으로 메모리 부족의 원인이 한 곳이라고 단정하지는 않았다.

## 대응과 설계

실행 중이라는 표시만으로는 부족했다. 실제 작업이 진행되는지 확인하려고 heartbeat 기반 상태 감시와 제한적 복구 장치를 추가했다.

- 상태 갱신이 멈췄는지 다시 확인한다. 시작 직후에는 유예를 두고, 재시작 간격과 횟수도 제한한다.
- 수동으로 중지했거나 배포 중인 상태는 그대로 둔다.
- 자동 조건주문이 명시적으로 꺼져 있고 필요한 운영 조건이 확인될 때만 복구한다.
- 시장이 닫혀 시세가 없는 상황을 장애로 처리하지 않는다.

메모리 부족 장애 때는 신규 자동 등록·수정을 중지한 상태에서 복구를 승인했다. 서비스를 복구하고 남아 있던 조회 프로세스를 정리했다. 기존 외부 주문과 거래 기록은 보존했다.

## 검증과 결과

복구 후에는 heartbeat가 움직이는지, 후보가 갱신되는지, 수신 시세가 늘어나는지, 최근 관측 시각이 바뀌는지를 함께 확인했다.

| 확인한 것 | 추가 확인이 필요한 것 |
|---|---|
| 커널 기록에 남은 메모리 부족 종료 | 단일 원인의 확정 |
| 복구 후 감시 처리 재개 | 장기간의 메모리 안정성 |
| heartbeat 기반 제한적 복구 장치 적용 | 모든 장애 유형의 자동 복구 |

이때 신규 알림이 기기에 도착하는 것까지 확인한 것은 아니다. 감시가 다시 진행된 건 확인했지만, 재발 원인까지 제거했다고 볼 수는 없다.
