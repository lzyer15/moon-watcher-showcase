# 사례 2 · 프로세스 실행과 실제 감시 진행을 구분하기

## 문제

작은 단일 VM에서 서비스 프로세스가 실행 중인데도 감시 heartbeat가 멈추는 장애가 있었습니다. 이후 메모리 부족에 의한 감시 프로세스 강제 종료도 커널 기록으로 확인했습니다.

화면 조회용 스트림 프로세스가 여러 개 남아 있는 현상도 관측했습니다. 이 사실만으로 특정 코드 한 곳을 메모리 부족의 유일한 원인으로 단정하지 않았습니다.

## 대응과 설계

프로세스 존재와 실제 작업 진행을 구분하기 위해 heartbeat 기반 상태 감시와 제한적 복구 장치를 추가했습니다.

- 상태 갱신 정체를 재확인하고 시작 유예와 재시작 간격·횟수를 제한합니다.
- 수동 정지와 배포 상태를 덮어쓰지 않습니다.
- 자동 조건주문이 명시적으로 꺼져 있고 필요한 운영 조건이 확인될 때만 복구합니다.
- 시장이 닫혀 시세가 없다는 이유만으로 장애라고 판단하지 않습니다.

메모리 부족 장애에서는 사용자 승인 후 신규 자동 등록·수정을 중지한 상태에서 서비스를 복구하고 남아 있던 조회 프로세스를 정리했습니다. 기존 외부 주문과 거래 기록은 보존했습니다.

## 검증과 결과

복구 후에는 실행 상태뿐 아니라 heartbeat, 후보 갱신, 수신 시세 증가와 최근 관측 시각을 함께 확인했습니다.

| 확인한 것 | 추가 확인이 필요한 것 |
|---|---|
| 커널 기록에 남은 메모리 부족 종료 | 단일 원인의 확정 |
| 복구 후 감시 처리 재개 | 장기간의 메모리 안정성 |
| heartbeat 기반 제한적 복구 장치 적용 | 모든 장애 유형의 자동 복구 |

이 복구 표본에서 신규 알림의 기기 수신까지 확인한 것은 아닙니다. 장애를 복구했다는 사실과 재발 원인을 제거했다는 사실을 구분했습니다.

## 배운 점과 다음 과제

서비스의 정상 여부는 사용자가 필요한 일이 진행되는지로 판단해야 합니다. 후속 작업은 이전 스트림 종료 확인, DB 연결 수명 관리, 작업별 자원 상한과 장시간 메모리·연결 수 비교입니다. 이 예방 작업은 아직 완료 성과로 제시하지 않습니다.
